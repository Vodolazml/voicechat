# Техническое задание на desktop-приложение для приватного общения

## 1. Назначение и продуктовая концепция

Программа представляет собой приватное desktop-приложение для голосового, текстового и визуального общения внутри закрытых серверов/пространств. По пользовательской логике и основным сценариям приложение должно быть близко к Discord: пользователь входит в доступное пространство, видит разрешенные ему каналы, подключается к голосовому каналу одним действием, видит список участников, управляет своим микрофоном, звуком и индивидуальными настройками других участников.

Продукт предназначен для небольших закрытых сообществ, команд, игровых групп, рабочих коллективов или частных организаций, которым требуется контролируемая среда общения, размещаемая на собственном сервере/VPS.

Ключевые принципы продукта:

- приватность и контроль доступа важнее публичной открытости;
- все действия с учетными записями и доступами должны быть управляемыми;
- голосовые каналы должны быть понятны пользователю без обучения;
- интерфейс должен выглядеть как готовый коммерческий продукт, а не как технический прототип;
- архитектура должна позволять расширять роли, права, серверы/пространства, каналы и медиа-функции без полной переработки системы;
- безопасность должна проектироваться как обязательная часть продукта, поскольку приложение будет доступно через интернет.

## 2. Общая модель продукта

Система состоит из desktop-клиента, backend-сервера, базы данных, медиа-подсистемы для голоса и screen sharing, механизма обновлений, панели администрирования и инфраструктурных компонентов.

Основные сущности:

- пользователь;
- администратор;
- сервер/пространство;
- канал;
- голосовой канал;
- текстовый канал;
- участник канала;
- роль;
- permission;
- сессия;
- аудио-состояние пользователя;
- сообщение;
- событие аудита;
- клиентское устройство.

В первоначальной продуктовой политике все учетные записи создает только администратор. Создание серверов/пространств и каналов также изначально доступно только администратору. При этом реализация должна быть построена на расширяемой системе прав, чтобы в будущем отдельные разрешения можно было выдавать обычным пользователям или ролям без изменения архитектуры.

## 3. Функциональные требования

### 3.1. Учетные записи

Приложение должно поддерживать централизованное управление учетными записями.

Требования:

- учетные записи пользователей создает только администратор;
- самостоятельная публичная регистрация пользователей не допускается;
- администратор может создать пользователя с временным паролем;
- пользователь при первом входе должен сменить временный пароль;
- администратор не должен иметь возможности посмотреть пароль пользователя;
- администратор может сбросить пароль пользователя;
- учетная запись может быть активной, заблокированной или удаленной логически;
- все административные действия с учетными записями должны попадать в audit log;
- имя пользователя должно быть уникальным в рамках системы или пространства в зависимости от выбранной модели;
- пользователь должен иметь отображаемое имя, которое может отличаться от логина;
- система должна поддерживать аватар пользователя, но отсутствие аватара не должно ломать интерфейс.

### 3.2. Серверы/пространства

Сервер или пространство является контейнером для каналов, участников и правил доступа.

Требования:

- архитектура должна поддерживать создание нескольких серверов/пространств;
- изначально право создания серверов/пространств доступно только администратору;
- право создания серверов/пространств должно быть оформлено как permission;
- администратор может добавлять и удалять пользователей из пространства;
- пользователь должен видеть только те пространства, к которым имеет доступ;
- каждое пространство должно иметь название, уникальный идентификатор, список участников, набор каналов и настройки прав;
- удаление пространства должно быть защищено подтверждением и попадать в audit log.

### 3.3. Каналы

Каналы являются основным способом организации общения.

Требования:

- приложение должно поддерживать голосовые и текстовые каналы;
- архитектура должна позволять добавлять дополнительные типы каналов в будущем;
- создание каналов изначально доступно только администратору;
- право создания каналов должно быть реализовано через систему permissions;
- администратор может добавлять пользователей в канал;
- администратор может удалять пользователей из канала;
- пользователь видит только те каналы, к которым имеет доступ;
- канал должен иметь название, тип, принадлежность к пространству, список разрешенных участников и настройки доступа;
- удаление канала должно быть защищено подтверждением;
- действия создания, изменения и удаления каналов должны логироваться в audit log.

### 3.4. Голосовые каналы

Голосовые каналы должны работать привычно для пользователей Discord.

Требования:

- пользователь может подключиться к доступному голосовому каналу;
- пользователь может выйти из голосового канала;
- при подключении к другому голосовому каналу пользователь автоматически отключается от предыдущего;
- в канале должен отображаться актуальный список участников;
- пользователи в одном голосовом канале должны иметь возможность разговаривать одновременно;
- интерфейс должен показывать состояние пользователя: говорит, muted, deafened, reconnecting, disconnected;
- пользователь может включать и выключать свой микрофон;
- пользователь может включать deafen: отключение входящего звука вместе с выключением собственного микрофона;
- пользователь может локально заглушить конкретного участника только для себя;
- пользователь может настроить индивидуальную громкость каждого участника;
- индивидуальная громкость и локальный mute должны быть локальными пользовательскими настройками и не влиять на других участников;
- пользователь может выбрать микрофон;
- пользователь может выбрать устройство вывода звука;
- приложение должно поддерживать reconnect при кратковременной потере сети;
- при reconnect клиент должен восстанавливать голосовой канал и локальные аудио-настройки;
- при невозможности reconnect пользователь должен получить понятное состояние ошибки;
- клиент должен корректно освобождать аудио-устройства при выходе из канала или закрытии приложения.

### 3.5. Текстовый чат

Текстовый чат является целевой функцией продукта и должен быть заложен в архитектуру как полноценная часть системы.

Требования:

- текстовые каналы должны поддерживать отправку и получение сообщений в реальном времени;
- пользователь видит только сообщения в каналах, к которым имеет доступ;
- сообщения должны иметь автора, время создания, принадлежность к каналу и уникальный идентификатор;
- система должна поддерживать историю сообщений;
- должна быть возможность редактирования своих сообщений, если permission это разрешает;
- должна быть возможность удаления своих сообщений, если permission это разрешает;
- администратор или пользователь с соответствующим permission может удалять сообщения других пользователей;
- удаление и модерация сообщений должны попадать в audit log;
- клиент должен отображать состояние доставки сообщения;
- клиент должен корректно работать при временной потере соединения;
- архитектура должна позволять добавить вложения, реакции, упоминания и поиск без переписывания модели сообщений.

### 3.6. Screen sharing

Screen sharing является целевой функцией программы и должен проектироваться как часть медиа-архитектуры.

Требования:

- пользователь может начать демонстрацию экрана в голосовом канале, если имеет соответствующее право;
- изначально право screen sharing может быть ограничено администратором или разрешено всем участникам канала по настройке;
- право демонстрации экрана должно быть permission;
- пользователь может выбрать весь экран или конкретное окно, если это поддерживается платформой;
- другие участники канала могут просматривать демонстрацию;
- интерфейс должен показывать, кто демонстрирует экран;
- пользователь может остановить демонстрацию;
- при потере соединения демонстрация должна завершаться или восстанавливаться по понятному правилу;
- должна быть возможность ограничить качество, FPS и bitrate демонстрации;
- архитектура должна учитывать приватность: клиент не должен начинать захват экрана без явного действия пользователя.

## 4. Роли и permissions

Система прав должна быть расширяемой с самого начала.

Минимальные роли:

- Owner/System Admin;
- Space Admin;
- User.

Начальная политика:

- учетные записи создает только администратор;
- серверы/пространства создает только администратор;
- каналы создает только администратор;
- администратор добавляет и удаляет пользователей из каналов;
- обычный пользователь может использовать только доступные ему каналы;
- пользователь не может сам выдавать себе права.

Примеры permissions:

- `users.create`;
- `users.disable`;
- `users.reset_password`;
- `spaces.create`;
- `spaces.update`;
- `spaces.delete`;
- `spaces.members.manage`;
- `channels.create`;
- `channels.update`;
- `channels.delete`;
- `channels.members.manage`;
- `voice.join`;
- `voice.speak`;
- `voice.mute_self`;
- `voice.deafen_self`;
- `voice.moderate`;
- `text.read`;
- `text.send`;
- `text.edit_own`;
- `text.delete_own`;
- `text.delete_any`;
- `screen_share.start`;
- `screen_share.view`;
- `audit.view`;
- `settings.manage`;

Требования к permissions:

- проверки прав должны выполняться на сервере, а не только в клиентском интерфейсе;
- клиент может скрывать недоступные элементы, но это не является защитой;
- права должны назначаться через роли и, при необходимости, индивидуальные overrides;
- система должна поддерживать наследование прав от пространства к каналам;
- конфликт прав должен разрешаться по документированному правилу;
- любое изменение ролей и permissions должно попадать в audit log.

## 5. GUI/UX

GUI является обязательной частью продукта. Не допускается интерфейс уровня технического прототипа, отладочной панели или простого набора стандартных кнопок.

Требования:

- приложение должно иметь полноценный, красивый, современный, коммерчески привлекательный desktop-интерфейс;
- допустимые технологии: PySide6, PyQt, Qt/QML, Electron, Tauri, Flutter Desktop, .NET MAUI, Avalonia или другой подходящий desktop framework;
- при использовании Python предпочтительны PySide6/PyQt с кастомной темой, современными компонентами и аккуратной адаптацией под Windows;
- дизайн должен выглядеть как продаваемый продукт: единый стиль, качественная типографика, продуманная цветовая палитра, плавные состояния, аккуратные отступы, понятные иконки;
- приложение не должно выглядеть как стандартное окно без дизайна;
- интерфейс должен быть удобен для ежедневного использования;
- основные действия должны быть доступны в 1-2 клика;
- структура интерфейса должна быть близка к Discord: список пространств, список каналов, основная область канала, список участников, нижняя панель пользователя и аудио-контролов;
- голосовой канал должен визуально показывать активных участников и говорящих пользователей;
- mute, deafen, выбор устройств, настройки громкости и выход из канала должны быть всегда быстро доступны;
- ошибки должны отображаться понятным человеческим текстом;
- reconnect должен показываться явно, без ощущения зависания приложения;
- интерфейс должен корректно работать при разных размерах окна;
- должны быть предусмотрены светлая и темная темы либо качественная темная тема как основная;
- важные destructive-действия должны требовать подтверждения;
- административные функции должны быть отделены от обычного пользовательского опыта и не перегружать основной интерфейс.

Ожидаемая базовая структура:

- левая колонка пространств;
- колонка каналов выбранного пространства;
- центральная область текущего канала;
- правая область участников, если применимо;
- нижняя панель текущего пользователя;
- панель голосового подключения;
- модальное окно настроек;
- административные экраны управления пользователями, каналами, ролями и правами.

## 6. Архитектура клиента и сервера

Система должна строиться как клиент-серверное приложение.

Рекомендуемая логическая схема:

```text
Desktop Client
  |
  | HTTPS / WSS
  v
Backend API
  |
  +-- PostgreSQL
  +-- Redis / cache / presence
  +-- Media service / SFU / WebRTC
  +-- Object storage for future attachments
```

Требования:

- клиент не должен напрямую обращаться к базе данных;
- все права и бизнес-правила проверяются на backend;
- realtime-события должны передаваться через WebSocket или аналогичный механизм;
- голос и screen sharing должны использовать WebRTC или другую подходящую media-технологию;
- backend должен иметь четкое разделение: auth, users, spaces, channels, permissions, messaging, presence, media signaling, audit;
- API должен иметь версионирование;
- серверная часть должна быть готова к развертыванию на VPS;
- внутренние сервисы не должны быть доступны напрямую из интернета;
- приложение должно быть удобно собирать, обновлять и сопровождать.

## 7. Голос и медиа

Рекомендуемый подход для медиа: WebRTC с SFU, например LiveKit, mediasoup, Janus или аналогичным решением.

Требования:

- передача голоса должна быть низколатентной;
- несколько пользователей должны говорить одновременно;
- клиент должен поддерживать echo cancellation, noise suppression и automatic gain control, если выбранный стек это позволяет;
- пользователь должен управлять input/output устройствами;
- клиент должен корректно обрабатывать смену устройства во время работы;
- локальные настройки громкости должны применяться на стороне клиента;
- mute микрофона должен прекращать отправку аудио или явно помечать track как muted;
- deafen должен отключать входящий звук и микрофон пользователя;
- сервер должен контролировать, имеет ли пользователь право подключиться к каналу;
- сигналинг должен быть авторизованным;
- media-сессии должны истекать и не должны жить бесконечно после потери сессии пользователя;
- для fallback-сценариев должен быть предусмотрен TURN-сервер.

Производительность для 10 пользователей:

- голосовой канал должен стабильно поддерживать до 10 одновременных участников;
- задержка голоса в нормальных сетевых условиях должна стремиться к уровню, комфортному для разговора;
- приложение должно оставаться отзывчивым при 10 участниках в голосовом канале;
- reconnect после краткой потери сети должен выполняться автоматически;
- CPU и RAM клиента должны оставаться в разумных пределах для обычного desktop-компьютера.

## 8. Текстовая подсистема

Требования:

- сообщения должны храниться в базе данных;
- доступ к истории сообщений должен проверяться по правам;
- realtime-доставка должна работать через WebSocket или аналогичный транспорт;
- при повторном подключении клиент должен синхронизировать пропущенные сообщения;
- сообщения должны быть защищены от XSS/HTML-инъекций в интерфейсе;
- сервер должен валидировать длину сообщений, формат и права отправителя;
- должна быть защита от спама через rate limiting;
- действия модерации должны логироваться.

## 9. Screen sharing

Требования:

- screen sharing должен использовать ту же или совместимую WebRTC-медиа-архитектуру;
- право запуска демонстрации должно проверяться сервером;
- клиент должен запрашивать у пользователя явное действие на старт захвата;
- участники должны видеть состояние демонстрации;
- система должна поддерживать ограничение качества, FPS и bitrate;
- при завершении демонстрации все связанные media tracks должны освобождаться;
- необходимо предусмотреть защиту от несанкционированного просмотра: смотреть демонстрацию могут только участники с доступом к каналу.

## 10. Безопасность приложения

Безопасность должна проектироваться как базовое требование, а не как дополнительная функция.

Общие требования:

- использовать TLS для всех внешних соединений;
- не публиковать базу данных, Redis и внутренние сервисы в интернет;
- все входные данные валидировать на сервере;
- все проверки доступа выполнять на сервере;
- хранить пароли только в виде стойких хэшей;
- применять принцип минимальных привилегий;
- разделять пользовательские и административные действия;
- вести audit log для важных операций;
- поддерживать безопасное обновление клиента;
- не хранить секреты в коде или репозитории;
- проектировать систему с учетом угроз публичного VPS.

## 11. E2EE

End-to-end encryption должна быть рассмотрена как целевое требование для приватности медиа и сообщений.

Требования:

- архитектура должна не блокировать внедрение E2EE;
- для голосовых и screen sharing потоков предпочтительно использовать WebRTC encryption и, при возможности, insertable streams или механизм E2EE, поддерживаемый выбранным SFU;
- сервер не должен получать доступ к расшифрованному содержимому E2EE-медиа, если E2EE включено;
- управление ключами должно быть спроектировано отдельно и документировано;
- необходимо предусмотреть компромиссы: E2EE может ограничивать серверную запись, транскрипцию, модерацию содержимого и некоторые media-функции;
- для текстового чата архитектура должна позволять добавить E2EE, но необходимо отдельно определить модель поиска, истории, восстановления доступа и устройств;
- пользователь должен понимать, включено ли E2EE для текущего канала или сессии.

## 12. Authentication и session management

Требования:

- пароли должны хэшироваться с помощью Argon2id или другого современного алгоритма с корректными параметрами;
- временный пароль должен быть одноразовым и требовать смены при первом входе;
- сессии должны иметь ограниченный срок жизни;
- refresh tokens, если используются, должны храниться безопасно;
- access tokens должны быть короткоживущими;
- должна быть возможность завершить активные сессии пользователя;
- при смене пароля старые сессии должны быть отозваны или помечены для повторной авторизации;
- административные аккаунты должны поддерживать MFA;
- необходимо защищаться от brute force: задержки, rate limiting, временная блокировка, аудит подозрительных попыток;
- cookie или token storage должны быть выбраны с учетом desktop-модели угроз;
- клиент не должен логировать токены, пароли или секретные данные.

## 13. Защита API

Требования:

- все API endpoints должны требовать аутентификацию, кроме явно публичных служебных endpoints;
- авторизация должна проверяться на каждом endpoint;
- API должен валидировать схемы запросов;
- ошибки API не должны раскрывать внутренние детали системы;
- должны применяться rate limits;
- CORS, если нужен, должен быть настроен строго;
- WebSocket-соединения должны проходить аутентификацию и авторизацию;
- signaling для медиа должен быть защищен от подключения посторонних пользователей;
- API должен иметь request-id для трассировки;
- небезопасные методы и debug endpoints не должны быть доступны в production.

## 14. Server/VPS hardening

Требования:

- использовать reverse proxy перед backend;
- включить TLS с современными настройками;
- закрыть все неиспользуемые порты firewall'ом;
- PostgreSQL, Redis и внутренние сервисы должны слушать только private interface или localhost;
- SSH должен быть защищен ключами, пароли для SSH должны быть отключены;
- root-login по SSH должен быть отключен;
- система должна регулярно обновляться;
- должна быть настроена базовая защита от brute force SSH;
- сервисы должны запускаться от отдельных пользователей с минимальными правами;
- секреты не должны храниться в shell history или открытых файлах;
- production-логи не должны содержать токены и пароли;
- должны быть настроены мониторинг доступности и алерты;
- резервное копирование должно быть автоматическим.

## 15. База данных

Рекомендуемая база данных: PostgreSQL.

Требования:

- хранить пользователей, роли, permissions, пространства, каналы, memberships, сообщения, сессии и audit log;
- использовать миграции схемы БД;
- применять индексы для частых запросов;
- использовать внешние ключи и ограничения целостности;
- не удалять критичные данные физически без необходимости: предпочтительно soft delete для пользователей, каналов и пространств;
- доступ приложения к БД должен выполняться через отдельного пользователя с минимальными правами;
- БД не должна быть доступна из интернета;
- резервные копии БД должны шифроваться;
- персональные и чувствительные данные должны храниться минимально необходимым образом.

## 16. Secrets management

Требования:

- секреты не должны храниться в git;
- production-секреты должны передаваться через переменные окружения, secret manager или защищенный конфигурационный механизм;
- разные окружения должны иметь разные секреты;
- токены, приватные ключи, ключи подписи и пароли БД должны ротироваться;
- доступ к секретам должен быть ограничен;
- секреты не должны попадать в crash reports, логи и telemetry;
- ключ подписи обновлений должен храниться максимально защищенно и отдельно от runtime-сервера.

## 17. Логирование и audit

Требования:

- приложение должно вести технические логи для диагностики;
- приложение должно вести audit log для значимых действий;
- audit log должен включать: кто выполнил действие, что изменил, когда, с какого IP/устройства, результат операции;
- в audit log должны попадать создание и блокировка пользователей, сброс пароля, изменение ролей, изменение permissions, создание/удаление каналов, добавление/удаление участников, удаление сообщений, административные действия;
- логи не должны содержать пароли, access tokens, refresh tokens, приватные ключи и содержимое E2EE-ключей;
- должна быть ротация логов;
- важные security-события должны быть доступны администратору.

## 18. Rate limiting

Требования:

- ограничивать попытки входа;
- ограничивать сброс пароля;
- ограничивать частоту API-запросов;
- ограничивать частоту WebSocket-событий;
- ограничивать отправку сообщений;
- ограничивать частоту reconnect;
- лимиты должны учитывать пользователя, IP и endpoint;
- превышение лимитов должно логироваться как security-событие;
- лимиты должны быть настраиваемыми для production.

## 19. DDoS и устойчивость

Требования:

- использовать reverse proxy с базовыми ограничениями запросов;
- иметь firewall-правила для закрытия ненужных портов;
- предусмотреть защиту media-сервисов от неавторизованного подключения;
- использовать TURN только с авторизованным доступом и ограниченным сроком credentials;
- иметь мониторинг нагрузки CPU, RAM, network, disk, database connections;
- при перегрузке система должна деградировать управляемо, а не падать без объяснения;
- публичные endpoints должны быть минимальными;
- production-развертывание должно позволять подключить внешнюю DDoS-защиту на уровне провайдера или reverse proxy.

## 20. Безопасные обновления и подпись установщика

Требования:

- desktop-клиент должен распространяться через подписанный установщик;
- обновления должны быть подписаны;
- клиент должен проверять подпись обновления перед установкой;
- обновления должны загружаться только по HTTPS;
- механизм обновлений не должен позволять подмену пакета;
- rollback должен быть продуман для неудачного обновления;
- ключи подписи должны храниться отдельно от основного backend;
- версия клиента должна отображаться в интерфейсе;
- сервер должен иметь возможность требовать минимальную поддерживаемую версию клиента.

## 21. Резервное копирование

Требования:

- резервные копии БД должны выполняться автоматически;
- backups должны храниться отдельно от основного сервера;
- backups должны быть зашифрованы;
- должен быть определен срок хранения backups;
- восстановление из backup должно периодически проверяться;
- необходимо документировать процедуру восстановления;
- критичные конфигурации сервера также должны иметь резервную копию;
- секреты и ключи должны резервироваться отдельно и безопасно.

## 22. Threat model

Необходимо учитывать следующие угрозы:

- подбор паролей;
- кража токена сессии;
- несанкционированный доступ к каналу;
- обход permissions через клиент;
- подключение к media-сессии без права доступа;
- XSS или injection через текстовые сообщения;
- SQL injection;
- утечка секретов из логов или репозитория;
- компрометация VPS;
- подмена обновления клиента;
- DDoS или resource exhaustion;
- злоупотребление reconnect и signaling;
- просмотр screen sharing посторонним пользователем;
- доступ администратора к данным сверх необходимого;
- потеря данных из-за отсутствия backup;
- downgrade клиента до уязвимой версии.

Для каждой угрозы в проектной документации должны быть описаны меры защиты, остаточный риск и способ проверки.

## 23. Производительность и масштабирование

Минимальная целевая нагрузка:

- 10 пользователей в одном пространстве;
- 10 пользователей в одном голосовом канале;
- одновременный разговор нескольких участников;
- работа текстового чата без заметных задержек;
- стабильный reconnect при кратковременной потере сети;
- корректная работа клиента на обычном desktop-компьютере.

Требования к масштабированию:

- архитектура должна позволять увеличить число пользователей без полной переработки;
- backend должен быть stateless там, где это возможно;
- presence и realtime-состояния можно выносить в Redis или аналогичный компонент;
- media-сервис должен быть масштабируемым отдельно от основного API;
- БД должна поддерживать индексацию и оптимизацию запросов;
- должна быть возможность горизонтально масштабировать API;
- архитектура должна позволять разделить text, voice/media, auth и admin-функции при росте нагрузки.

## 24. Администрирование

Требования:

- администратор должен иметь отдельные экраны управления пользователями;
- администратор должен управлять пространствами;
- администратор должен управлять каналами;
- администратор должен добавлять и удалять пользователей из каналов;
- администратор должен управлять ролями и permissions;
- администратор должен видеть audit log;
- администратор должен иметь возможность блокировать пользователя;
- административный интерфейс должен быть удобным и визуально согласованным с основным приложением;
- опасные действия должны требовать подтверждения.

## 25. Нефункциональные требования

Требования:

- приложение должно быть стабильным при длительной работе;
- клиент не должен зависать при потере соединения;
- интерфейс должен оставаться отзывчивым во время голосового соединения;
- ошибки должны быть понятными;
- production-сборка не должна содержать debug-инструментов;
- конфигурация окружений должна быть отделена от кода;
- проект должен иметь документацию по установке, запуску, обновлению и восстановлению;
- основные security-механизмы должны покрываться тестами;
- критичные API должны иметь автоматические тесты;
- сборка клиента и сервера должна быть воспроизводимой.

## 26. Критерии приемки

Продукт считается соответствующим требованиям, если:

- администратор может создать пользователя;
- пользователь может войти только с корректными учетными данными;
- пользователь обязан сменить временный пароль при первом входе;
- администратор может создать пространство и канал;
- права создания пространства и канала реализованы через permissions;
- администратор может добавить пользователя в канал и удалить его оттуда;
- пользователь видит только доступные ему каналы;
- пользователь может подключиться к голосовому каналу и выйти из него;
- список участников голосового канала обновляется в реальном времени;
- несколько пользователей могут говорить одновременно;
- работают mute, deafen, локальный mute другого пользователя и индивидуальная громкость;
- пользователь может выбрать микрофон и устройство вывода;
- reconnect работает при кратковременной потере сети;
- текстовый чат заложен и реализован как целевая подсистема;
- screen sharing заложен и реализован как целевая media-функция;
- все важные права проверяются на сервере;
- пароли не хранятся в открытом виде;
- API защищено аутентификацией, авторизацией, валидацией и rate limiting;
- БД и внутренние сервисы не доступны из интернета;
- есть audit log административных и security-событий;
- есть стратегия backup и восстановления;
- desktop-клиент имеет современный коммерческий GUI и не выглядит как технический прототип;
- установщик и обновления имеют механизм подписи и проверки.

## 27. Итоговое требование к качеству продукта

Программа должна восприниматься пользователем как готовый приватный аналог Discord/TeamSpeak для закрытого общения: современный интерфейс, быстрый вход в голосовой канал, понятные аудио-контролы, безопасная авторизация, строгий контроль доступа, управляемая серверная архитектура и возможность дальнейшего расширения без переписывания ядра.

Безопасность, permissions, GUI и media-архитектура являются обязательными частями продукта, а не дополнительными улучшениями.
